# 從展示到實際量測

目前網站是互動概念模型，不是已校正的球場複本，也不是硬體擷取系統。新版能記錄及匯出**模擬投球**，沒有實測影像、雷達訊號、球種模型或正式 ABS 資格。場地長寬、人物、設備與視野需在場勘後替換。

## 能力與前置條件

2026-09-28 v3.0更新：一期已要求普通未加人工標記球的直接轉速與三維有向軸，不能延後或改用球路推估驗收。主案4相機＋24GHz，FPGA/60GHz為選配平行研究。詳見[公開計畫](open-sensor-plan-v3.md)。

| 目標 | 最小資料與設備 | 完成條件 |
| --- | --- | --- |
| 球種記錄 | 事件 ID、投手 ID、人工球種標籤 | 先人工記錄，再用已標註的球速、位移、釋球點及旋轉特徵訓練分類器；未知球種可拒判 |
| 進壘點、球速 | 本壘至少兩個有效同步視角、內外參、時間戳、球心；軸向雷達輔助 | 對獨立真值量測偏差、尾端誤差、漏球及遮擋；相機數量不等於可用視角數量 |
| 轉速、轉軸 | 看得清球縫的連續短曝光影像、球體三維姿態 | 先確認球縫像素數與旋轉取樣混疊；普通球心追蹤不足 |
| 打擊球路 | 擊球前後高速影像與擊出球三維軌跡 | 另驗證擊球初速、球的仰角、方向；追完整飛行才能記錄實際落點 |
| 揮棒與比賽數據 | 揮棒／接觸事件、完整打席狀態、正式記錄 | 記錄 ID 對齊；含界外、擦棒、犧牲打、失誤、故意四壞等例外 |
| 守備與跑壘 | 全場球員位置與身分、球軌跡、接傳球／觸壘／成敗事件 | 牛棚配置不足；需全場覆蓋、重識別與跨鏡同步 |
| OAA 類、xBA 類 | 當地大量標註樣本與經驗模型 | 自建模型須報告校準、資料切分與樣本外誤差，不宣稱數值等同官方 |
| ABS 訓練輔助 | 本壘幾何、球體軌跡、好球帶設定、誤差與校正證據 | 先以影子模式與獨立真值比較；正式判決另需球團／聯盟採用規則與驗收 |

「所有進階數據」應先凍結一份球團簽認的欄位清單。CPBL 清單是起點，並未涵蓋所有可能的守備或球棒指標。每一個指標都要定義分子、分母、排除條件、單位、座標、球季、版本、缺值處理及來源。

## 原始資料不能只保存計算結果

1. **事件身分**：比賽／訓練 ID、打席 ID、逐球 ID、投打捕與守備員 ID、左右手、既有身高資料及量測日期；不需球員體重。
2. **相機擷取**：frame ID、感測器 ID、硬體時間戳、曝光、增益、影像／ROI 檔案位置、解析度、裁切原點、像素格式、丟幀。ROI 須能回推原圖座標。
3. **光學偵測**：球心像素、半徑、球縫或姿態特徵、球棒端點、球員關節／位置、可見性與信心；保留模型版本。
4. **雷達擷取**：I/Q 或 ADC 事件片段、取樣率、chirp／天線設定、頻率、range–Doppler／角度結果、SNR、歧義旗標、時間戳與單位。
5. **校正與同步**：內參、鏡頭畸變、外參、球場控制點、時間偏移與漂移、校正版本／溫度／日期、驗證誤差。共同偏差不會因為增加節點就消失。
6. **融合軌跡**：時間序列 p(t)、v(t)、協方差／誤差估計、每筆來源 ID、失追區間、擬合殘差、重建版本。原始、融合、推估、人工修正分開存。
7. **比賽事件**：揮棒、揮空、接觸、界外、場內、擊球型態、接球、傳球、觸壘、安打類別與正式結果；保留修訂歷程。
8. **稽核與運維**：韌體／FPGA／模型／規則版本、節點健康、處理及發布時間戳、延遲、封包遺失與拒判原因。

Demo 匯出的 `trajectory.samples` 是生成的資料，**不是以上硬體原始資料**。`acquisition` 尚未實作擷取，只保留空欄位示範；正式版本要建立物件儲存、事件資料庫與取得授權的後端。

## 工程路線

先在既有研發電腦上做可重播的離線管線：擷取 → 對時 → 校正 → 球體偵測 → 多視角重建 → 雷達殘差檢查 → 指標 → 品質閘門 → 儲存與顯示。保留同一套介面，先用錄影／雷達檔取代即時輸入，再接現場串流。

演算法穩定後量測瓶頸，逐項將時間戳、ROI、前處理或固定模型推論移到 FPGA。預訓練權重需要相容架構、量化、編譯與推論 runtime，不能將圖片或通用模型檔直接放進 FPGA 就得到高速視覺。高用量不是效益指標；應看延遲、吞吐、功耗與維護成本。

24 GHz Doppler 先作徑向速度交叉檢查；`fD = 2 vr / λ`，只有視線方向的速度，CW 模組不自帶距離。60 GHz 的距離、速度及角度能力取決於波形／天線／取樣設定；高速小球、最大不模糊速度、RCS、網子／球棒雜波需要實測。參考 [TI 雷達參數說明](https://e2e.ti.com/support/sensors-group/sensors/f/sensors-forum/1050220/faq-computing-maximum-range-velocity-and-resolution-mmwave-system)。增加節點應以改善遮擋、交會角、獨立備援為依據，同頻雷達要考慮互擾與排程。

## ABS 的驗證方式

先由使用單位指定判定平面或三維區域、球體交界規則、身高／姿態取得方式及異常處理。Demo 使用的 MLB 比例只是可視化參考，不應直接當成 CPBL 或特定球團規則。

測試至少分層報告：左右／上下位置偏差、95%／99% 誤差、邊界球結果、失追率、拒判率、同一球重播一致性、照明／雨水／不同球速／打者與捕手遮擋、支架震動與校正漂移。真值不能用同一組相機的輸出去證明自己正確。精度門檻和樣本量由預期用途與聯盟驗收要求決定，現在不能宣稱達標。

`1 ms × 40 m/s = 4 cm` 是球在那段時間的行進距離，說明對時不可忽略；它不是所有情況下都等於 4 cm 的進壘點誤差。相機幾何、內插方法和融合模型共同決定最終誤差。

## 即時性

逐筆保存 `capture → edge → fusion → decision → publish → visible display` 時間。v3.0定義最早納入的感測取樣到本地畫面實際可見 **≤800ms**，含必要觀測窗、傳輸與渲染。記錄觀測起終、P50/P95/P99、最大值及deadline miss；只看平均或瀏覽器回呼不夠。跨主機時鐘須校準；最終用共同trigger、LED/高速攝影或光電方式驗到畫面發光。

進壘點可以在投球到達判定面後輸出；落點、接球成功和完整守備成績要等相應事件結束。尚未結束時顯示的飛行終點、接球機率是**預測**。Demo慢動作回放2.4秒不是擷取/推論延遲，也沒有證明達成800ms；GitHub Pages不提供本地現場即時性SLA。4公頃能否布線仍待場館確認。
